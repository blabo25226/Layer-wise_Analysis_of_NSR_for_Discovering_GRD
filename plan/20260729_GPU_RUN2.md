## 1. 目的

GPU_RUN2では、GPU_RUN1で判明した計算量爆発、Colab切断、CPU律速、設定の途中変更を解消し、Phase 0–9を最初から一貫した計算budgetで再実行する。

READMEで定めた研究目標に従い、GPU_RUN2の目的を次の順で置く。

1. **メイン目標**：遺伝子制御ネットワークの動的方程式を求めるニューラルシンボリック回帰の層を解析する。
2. **サブ目標1**：層解析の知見を利用し、シンボリック回帰としてのsymbolic recovery精度を向上させる。
3. **サブ目標2**：合成データで検証した方法をDREAM4とヒト時系列へ適用し、新しいGRN候補方程式を発見する。

したがって、少数層fine-tuningによる計算削減だけを成功条件にしない。層表現のprobe、fine-tuning、
ablation、表現類似度、activation介入がどの程度一致するかを調べ、各層が入力表現、変数選択、
token生成、式構造回復のどこへ寄与するかを主結果として残す。

中心目的は、単に短時間で終えることではなく、次を同時に満たすことである。

1. validation/test分離とpaired seedを守る
2. 全条件へ同じ探索budgetを与える
3. pathologicalなtargetに総時間を支配させない
4. failureを隠さず保存する
5. Colab GPU時間とcompute unitsをGPUが必要な処理へ集中させる
6. 切断後に完了済みtarget/foldを再計算しない

GPU_RUN1の確定結果と詳細な考察は
[`results/GPU_RUN1_report.md`](../results/GPU_RUN1_report.md)を参照する。
GPU_RUN2はGPU_RUN1を無かったことにして同じ探索を繰り返すrunではない。
GPU_RUN1で支持された少数層fine-tuningの全層同等性を独立に確認するとともに、
未確定だったtop層とrandom層の差、層ごとの機能、高次元変数選択、構造回復、
公平なPySR/TPSR比較、新しい候補方程式の提示を重点的に検証する。

| Top 1〜3は全層FTとNMSE同等性margin内で同等だった（paired差の上側信頼限界は最大`0.0093`） | 独立runで再現性とresource削減を確認し、marginを`0.02`へ狭めて事前登録する |
| Top 3対random 3の95%信頼区間は0を含んだ（`+0.0024 ± 0.0037`） | random集合反復を10本以上へ増やし、encoder限定・下位限定の対照を追加してrankingの付加価値を主検証する |
| test（未知骨格のみ）のskeleton recoveryは全条件で0だが、validation（訓練済み骨格）では全層FTのskeleton recoveryが`0.653`、`decoder_3`が`0.528`、encoder系が約`0.11`、pretrainedが`0.000`と層別に単調だった | testを2層化して両方を報告し、構造回復を層解析の主指標へ昇格する。validation側の値は必ずin-distributionと明記する |
| test骨格`hill_act_n4`／`hill_rep_n3`では、有理関数の形と変数集合（variable F1 0.92–1.00）は再現されるがHill係数だけが訓練分布へ張り付いた | 外挿限界としてそのまま報告し、指数のみの後処理最適化または条件付きdecodeをoperator ablationとして分離検討する |
| `mass_action`・`toggle_n2`では指数集合一致が`1.00`でもskeleton recoveryがほぼ0だった | 因数分解・定数吸収に非感応な指標が偽陰性を出しているため、代数正規形比較を先に実装する |
| TPSRは小さい追加改善に対して約55倍の記録elapsedを要し、selective FT後は追加利得の95% CIが0を跨いだ（交互作用`-0.0202 ± 0.0175`はCIが0を含まない） | 全条件で当然に実行せず、事前profilerを通った場合だけ副次比較する。交互作用は事前登録した再現対象として扱う |
| DREAM4はoracle regulators（edge F1約0.85）を与えてもpenalized NMSEが`0.855`–`0.943`にとどまった | selector改善を中心課題から外し、微分推定と分布ギャップの切り分けを先に行う |

| `tan`と危険な除算を含む式が多かった | operator allowlistと強化した安全性検査を必須にする |

### 1.2 事前に固定する主判定

GPU_RUN2では、結果を見てから成功基準を組み替えない。最低限、次を別々に判定する。

1. **層の役割と再現性**：probe、単一層fine-tuning、ablation、表現類似度、activation介入が示す
   重要層と機能を比較し、その順位と役割がseed、motif、GRN networkを越えて安定するかを報告する。
   相関的なprobe結果と、ablation・介入による因果的な寄与の証拠を区別する。
2. **全層同等性**：Top 1〜3と全層FTのfailure-penalized NMSE差について、95% t区間全体が
   事前margin `[-0.02, 0.02]`へ入るか。GPU_RUN1のmargin `0.05`はfine-tuning全体の効果
   `0.0793`の63%に相当し緩すぎた。実測のpaired CI上限は最大`0.0093`（効果の11.7%）であり、
   `0.02`でも同等性の結論は保たれると予測する。**この値は結果を見る前に固定し、事後に変更しない**。
3. **rankingの付加価値**：Top条件と事前生成したrandom層集合平均のpaired NMSE差について、
   95% t区間全体が0未満になるか。非有意差を同等性または優越性と呼ばない。
   GPU_RUN1では12層から3層を無作為抽出するとdecoder上位層を含む確率が高く、
   random baselineが強すぎた。rev.2では対照を3種類（全層random、encoder限定random、寄与下位random）へ分ける。
4. **構造回復**：exact、skeleton、symbolic equivalence、variable F1を条件別に、
   かつ **test 2層（訓練骨格のheld-outインスタンス／未知骨格）別に** 報告する。
   NMSEが同等でも訓練骨格側の構造回復が0なら、数式回復仮説は支持しない。
   未知骨格側の0は外挿限界の測定であり、fine-tuningの失敗と読み替えない。
   skeleton一致は代数正規形比較で判定し、`exact`（literal一致）と混同しない。
5. **decode時探索とfine-tuningの交互作用**：selective FT後にTPSRの追加利得が縮小するか。
   GPU_RUN1の交互作用は`-0.0202 ± 0.0175`でCIが0を含まなかった。GPU_RUN2ではこれを
   事前登録した再現対象とし、2×2（beam/TPSR × FTなし/selective FT）のpaired設計で判定する。
6. **高次元転移**：DREAM4 Size100の全5 networksで、経験的selectorとoracleのedge F1および
   failure-penalized NMSEの差を報告する。ただしGPU_RUN1ではoracle regulatorsでも
   penalized NMSEが`0.855`–`0.943`であり、平均予測器（NMSE = 1）をわずかに下回るだけだった。
   したがってGPU_RUN2では、まず微分推定sanity check（3.8節）で
   「NMSE約0.9が微分推定由来かモデル由来か」を切り分けてから転移結果を解釈する。
7. **実データ比較**：ヒトLODOではdonor fold内平均をseed単位に集約し、NeSymReSとPySRを同一operator・
   同一budget方針で比較する。これは予測的applicationであり、因果ODE回復の検定ではない。
   GPU_RUN1ではdonor 11で方法の順序が逆転しており、`n=4` donorでの順位づけは主張しない。
8. **候補方程式の発見**：DREAM4とヒト時系列では、低NMSEだけで候補を選ばず、holdout性能、valid rate、
   variable F1、式複雑度、特異点、外挿安定性、非負性を併記する。ヒトデータの式は「真の方程式」や
   「因果機構」ではなく、後続実験で検証すべき候補方程式として扱う。

seed数とrandom集合数は、本実行前にvalidation/pilot分散から検出力を検討して固定する。
計算資源だけを理由に減らす場合は、結果を見る前に計画を改訂し、縮小runとして明示する。

## 2. GPU_RUN1から引き継ぐ前提

- Python 3.10を維持する
- noiseは`0.1`だけを使用する
- Google Driveを永続保存先にする
- data、checkpoint、大規模成果物はGitへ入れない
- Phase 4の層選択はvalidationだけで行う
- testは方法固定後の最終評価だけに使う
- failure-penalized NMSE、valid rate、出力式、失敗理由を保存する
- seed内の比較条件では初期checkpoint、データ順、乱数状態をそろえる
- Colab上のcode commitを固定し、実行中にcodeを変更しない
- GPU_RUN1のtest結果を使ってGPU_RUN2の層、timeout、operatorを途中変更しない
- GPU_RUN1とGPU_RUN2を独立runとして保存し、結果を同一世代のseed反復へ混ぜない

## 3. GPU_RUN2の主要変更

### 3.1 層解析とprobingを先に行う

全層・全条件を本budgetで直接走らせる前に、validation上の軽量probingを行う。

probingの目的:

- 各層の表現がGRN式、変数選択、微分予測へどれだけ有用かを安価に測る
- 明らかに寄与の小さい層を高価なPhase 4候補から除外する
- encoder/decoderのどちらへ寄与が集中するか確認する
- full fine-tuningを基準として、単一層・少数層の改善方向を確認する
- 各層が入力表現、変数選択、token生成、式構造回復のどの段階へ寄与するかを仮説化する

候補となるprobing:

- frozen modelの各層hidden stateに対するlinear probe
- validation NMSEまたはtoken CEの小規模probe
- 少数の固定validation問題に対する層ごとの勾配norm
- CKAなどによる層表現の類似度
- 層ablationとactivation patchingなどの介入
- activation差分またはparameter update感度
- Phase 3の短時間layer scan

probingの結果から層候補を固定してから本実行へ進む。test結果を候補選択へ使わない。
GPU_RUN1で`decoder_2`〜`decoder_4`が上位だったことは再現対象であり、
GPU_RUN2のprobe結果を上書きする固定rankingとしては使わない。
linear probe、CKA、勾配normは相関的な証拠、ablationとactivation介入は機能的・因果的寄与に近い証拠として
区別して保存する。単一指標だけから層の役割を断定しない。

想定フロー:

```text
全層
  ↓ validation probing
上位候補層を5–8層へ絞る
  ↓ 小規模なpaired contribution評価
top / middle / bottomを固定
  ↓ GPU本実行
Phase 4–8
```

候補削減用のprobeはvalidation手続きとしてmanifestへ記録する。一方、固定済みの解析設計で行う
層表現・ablation・activation介入の比較は、メイン目標に対応する主結果として保存する。

### 3.2 演算子セットを制限する

GPU_RUN1では、`tan`、三角関数、危険な除算、特異点を含む式が生成され、BFGS・簡約・外挿評価の時間と不安定性を増やした。

GPU_RUN2の基本演算子候補:

- `+`
- `-`
- `*`
- safe divisionまたは厳しく制限した`/`
- `square`
- 必要なら整数の小さいべき乗

初期の主実行から除外する候補:

- `sin`
- `cos`
- `tan`
- 逆三角関数
- 任意実数べき乗
- 無制限の`exp`
- 無制限の`log`
- 特異点を作りやすい入れ子除算

実装上の注意:

- NeSymReSのpretrained vocabulary自体を不用意に変更しない。
- decode時のtoken mask、候補filter、または許可演算子のみを通す後段検査で対応する。
- PySR、NeSymReS、TPSRで可能な限り同じ演算子集合を使用する。
- 除外によって真の合成式を表現不能にしないよう、合成データgeneratorの式集合と整合させる。
- operator制限後のvalid rate、NMSE、complexity、variable F1を記録する。
- 三角関数が必要な別研究質問は、主実行と混ぜずoperator ablationとして分ける。
- token mask後に許可外演算子が残った候補は成功扱いにせず、理由付きfailureとして保存する。
- safe divisionは分母の最小絶対値、外挿grid、trajectory上の有限性を検査し、手法間で同じ判定を使う。

### 3.3 timeoutを最初から15秒へ統一する

GPU_RUN2では、1 targetのdecode hard timeoutを原則15秒にする。

```text
LANSR_DECODE_TIMEOUT_SEC=15
LANSR_PHASE8_DECODE_TIMEOUT_SEC=15
```

重要事項:

- run途中でtimeoutを変更しない。
- 同じ比較に含めるseed、network、conditionでは同じ15秒を適用する。
- timeoutを空の成功結果として扱わず、`DecodeTimeout`として保存する。
- valid rateとfailure-penalized指標へ反映する。
- target単位の実時間分布を保存する。
- p50、p90、p95、最大値、timeout率をPhase・条件別に可視化する。
- search内部timeoutと親processのhard timeoutを区別して保存する。

15秒の妥当性は本実行前のvalidation probeで確認する。

候補:

- 5秒
- 10秒
- 15秒
- 30秒

ただしGPU_RUN2の主実行budgetは、事前に15秒へ固定する想定である。比較後に都合のよいtimeoutをtest結果から選ばない。

### 3.4 CPUを100%使用する計算はローカルへ移す

Colab L4上でCPU処理を長時間実行すると、GPUが遊んでいてもcompute unitsを消費する。

原則としてローカルへ移す処理:

- PySR
- データdownloadとchecksum
- CPUだけの前処理
- JSON/CSV集計
- confidence interval計算
- manifest検査
- 図表生成
- archive作成
- CPUだけで完結するparameter fitting

個別判断が必要な処理:

- TPSR
  - MCTSはCPU負荷が高いが、Transformer推論はGPUを使える。
  - profilerでGPU利用率が低ければローカルまたはCPU専用queueへ分離する。
- NeSymReS + BFGS
  - Transformer推論はGPU、BFGSはCPU側である。
  - 完全なローカル移行ではなく、短いtimeoutとoperator制限でCPU律速を抑える。

ローカルとColabの成果物は同じrun IDとseed/fold/network命名規則を使い、統合時に次を照合する。

- source commit
- data fingerprint
- seed
- operator set
- timeout / iteration budget
- equation schema
- PySR/Julia version
- CPU情報
- parallelismとdeterministic設定
- search timeoutとprocess hard timeout

### 3.5 decodeを一度だけ行い複数splitで評価する

train/validation/testまたはin-donor/holdoutごとに同じ式を再生成しない。

正しい流れ:

```text
train dataで式を1回生成
  ↓
生成式を固定
  ├─ train/in-donorで評価
  ├─ validationで評価
  └─ 最終的にtest/holdoutで評価
```

これにより計算量を減らし、splitごとに異なる式を生成して比較が曖昧になる問題も防ぐ。

### 3.6 target/fold単位checkpointを全長時間Phaseへ適用する

最低保存単位:

- Phase 4: seed × layer × condition
- Phase 5: seed × condition
- Phase 6: seed × method × problem
- Phase 7: seed × size × network × condition × target
- Phase 8: seed × donor fold × method × target

保存内容:

- 完了target ID
- RNG stateまたはfold/target固有seed
- elapsed seconds
- raw/simplified equation
- candidate equations
- metric
- failure reason
- timeout flag
- search時間と総process時間
- 使用operatorと候補評価数

Drive同期は2–3分ごとに行い、workerは一定target数ごとにrecycleする。

### 3.7 smokeは最小限にする

smokeは研究結果として使用しない。

本実行前に確認するのは次だけとする。

- import
- CUDA認識
- checkpoint architecture
- 1–2 targetのdecode
- output schema
- Drive同期
- resume
- timeout
- failure保存

smokeが通った後は同じ本設定で直ちに本実行へ進む。

### 3.8 test集合を2層化する

GPU_RUN1の合成suite（180問）では、骨格レベルでtrainとtestが完全に分離していた。

| split | 問題数 | 骨格 |
|---|---|---|
| train | 120 | `additive_act`, `hill_act_n2`, `hill_act_n3`, `hill_rep_n2`, `linear2`, `mass_action`, `michaelis`, `self_act_n2`, `sqrt_sat`, `toggle_n2` |
| test | 60 | `hill_act_n4`, `hill_rep_n3`, `product_hill`, `ratio_xy`, `sum_linear3` |

リーク防止としては正しいが、testが「未知の関数族への外挿」だけを測るため、
fine-tuningが式回復へ寄与したかを test 上で一切測れない。実際、
validationのskeleton recoveryは層別に単調（全層FT `0.653`）である一方、testは全条件0だった。

GPU_RUN2では test を次の2層に分け、**別々に集計・報告する**。

| test層 | 構成 | 測るもの |
|---|---|---|
| `test_in_skeleton` | 訓練骨格のheld-outインスタンス（係数・初期条件・motif配線が異なる） | fine-tuningによる式回復の寄与（in-distribution） |
| `test_novel_skeleton` | 訓練に存在しない骨格 | 未知関数族への外挿限界 |

実装上の注意:

- suite generatorの分割規則を変更するだけでよく、追加のGPU計算は生じない。
- 2層は同一のdecode結果から評価し、層ごとに別decodeを行わない（3.5節）。
- 骨格IDは式IDから末尾のインスタンス番号を除いて同定し、`index.json`へ明示的な`skeleton`列を持たせる。
- validationについても骨格overlapを記録する。GPU_RUN1のvalidationは
  motif文字列が全問一意だったためグループ分割が事実上ランダム分割へ退化し、
  validation側9骨格はすべてtrainにも存在した。GPU_RUN2でも同様なら、
  validation recoveryは**in-distribution性能**と明記する。
- 主張文では必ず split 名を添える。「skeleton recoveryは0だった」という
  split非明示の記述はGPU_RUN2の成果物で使わない。

### 3.9 skeleton比較を代数正規形化する

GPU_RUN1のrecoveryは、定数をプレースホルダへ置換した文字列比較（`sym_recovery`）だけで担われており、
literal一致（`exact`）とsympy簡約による同値判定（`equiv`）は全条件で0だった。
さらに、代数的に同値でも因数分解形や定数吸収が異なると偽陰性になる。
実例として、validationの`mass_action`は指数集合一致`1.00`に対しskeleton recovery `0.000`、
`toggle_n2`は指数集合一致`1.00`に対し`0.111`である。

GPU_RUN2での対応:

- 指標名を`skeleton_recovery`へ改め、`sym_recovery`を「式回復率」と呼ばない。
- 比較を代数正規形で行う。最低限、sympyの`cancel`／`factor`／`together`後の比較を入れ、
  可能なら係数を自由変数として構造同型を判定する方式へ置き換える。
- 判定は3段階（`exact`＝literal一致、`skeleton`＝正規形での構造一致、`equiv`＝数値・記号同値）を
  別列で保存し、集計時に混ぜない。
- 正規形化のtimeoutと失敗（sympyのhang、簡約不能）は成功扱いにせず理由付きで保存する。
- GPU_RUN1の保存済みper-problem記録に対しても同じ正規形比較を適用し、
  metric artifact分がどれだけ回復するかをGPU_RUN2開始前に確認する（再学習不要）。

### 3.10 統計設計を事前登録する

GPU_RUN2の主判定は、実行前に次の値を固定する。

| 項目 | rev.1 | rev.2で固定する値 | 理由 |
|---|---|---|---|
| equivalence margin（penalized NMSE） | `0.05` | `0.02` | `0.05`はFT効果`0.0793`の63%。実測CI上限`0.0093`から`0.02`でも結論は保たれる |
| random層集合のdraw数 | 未定（GPU_RUN1は3本） | 10本以上 | draw 3本・seed 3本では検出力が不足 |
| random層集合の抽出母集団 | 全層 | 全層／encoder限定／寄与下位の3種類 | 全層randomはdecoder上位層を含みやすく対照として強すぎる |
| seed数 | 未定 | pilot分散から事前決定し、減らす場合は結果を見る前に改訂 | 事後の検出力調整を防ぐ |

判定規則:

- 全層同等性（TOST型の判定）とtop対random優越性（片側paired検定）は**別仮説**として扱い、
  一方の結果でもう一方の結論を補強しない。
- 非有意（CIが0を跨ぐ）を「同等」と書かない。GPU_RUN1のtop-3対random-3
  （`+0.0024 ± 0.0037`）は未支持であり、GPU_RUN2でも未支持なら未支持と報告する。
- bottom_3が明確に劣った（`0.0246`対top_3 `0.0150`）事実は、
  「どの3層でも同じではない」ことの証拠として別に報告する。

### 3.11 微分推定のsanity checkを転移実験より先に行う

GPU_RUN1のDREAM4では、oracle regulatorsを与えてもpenalized NMSEは`0.855`–`0.943`で、
平均予測器（NMSE = 1）をわずかに下回るだけだった。
すなわち regulator selection を完全に解決しても転移性能は改善しない。
残る候補原因は次の3つである。

1. 有限差分ターゲットが真のODE微分の代理として質が低い。
2. NeSymReSのpretraining分布（低次元・少数演算子・平滑な関数）がDREAM4の生成過程から遠い。
3. 21時点 × 10 replicate、`p=100`ではtargetあたりの有効サンプルが不足している。

GPU_RUN2では、DREAM4本実行の前に最小の切り分け実験を置く。

- **Phase 7a — sanity check**：真のODEが既知のDREAM4-like合成系で、
  (i) 真の解析微分、(ii) 有限差分、(iii) スプライン平滑化微分、(iv) 積分形式（弱形式）の
  4条件で同一のdecodeパイプラインを走らせ、penalized NMSEを比較する。
- 真の微分でNMSEが十分下がるなら原因は微分推定であり、
  下がらないならモデル・分布側であると判定する。
- この判定結果を、Phase 7本実行の解釈とselector改良への資源配分の根拠として記録する。
- GPU計算量は小さく（合成系・少数target）、GPU_RUN2全体のbudgetを圧迫しない。

READMEが未解決課題の先頭に置く「Size100のselector問題」は、**転移失敗のボトルネックとは確認されていない**。
selector改良を主課題として資源配分しない。

### 3.12 手法間のbudgetを統一する

GPU_RUN1のヒトLODOでは、PySRが`pysr_iterations = 12`・`search_timeout_sec = 15`・local CPUである一方、
NeSymReS側は`decode_timeout_sec = 30`にGPU上のselective fine-tuningが加わっていた。
budgetが桁で異なるため、この比較は方法の優劣の証拠にならない。

GPU_RUN2の統一規則:

- 比較に載せる全手法（NeSymReS beam、TPSR、PySR）へ、target単位で
  **同一のwall-clock budgetと同一のoperator set**を与える。
- wall-clockに加えて候補評価回数（beam幅×step、MCTS rollout、PySR population×iterations）を必ず併記する。
- ハードウェアが異なる比較（GPU decode 対 CPU PySR）は、
  「同一wall-clock・異種ハードウェア」であることを表・本文の両方へ明記する。
- fine-tuningに要したGPU時間は、decode budgetとは別項目として記録し、合算も併記する。
- budgetを揃えない参考値を載せる場合は、表側に「budget未統一の参考値」と明示する。
- PySRを本来の探索能力で走らせる高budget条件を別に置く場合は、
  主比較へ混ぜず、`pysr_high_budget`として別条件で報告する。

## 4. Phase別実行案

### Phase 0: environment / preflight

- Python 3.10
- source commit lock
- CUDA、checkpoint、data checksum
- operator mask確認
- 15秒timeout確認
- Drive write/read確認
- local/Colab成果物schema確認

### Phase 1: data

- noise=`0.1`
- motif・式構造・問題単位split
- testを`test_in_skeleton`と`test_novel_skeleton`へ2層化（3.8節）
- `index.json`へ`skeleton`列を追加し、split間の骨格overlapを実測して保存
- validationの骨格overlapを記録し、in-distributionかどうかを明示
- data fingerprint保存
- operator制限後も真式が表現可能か検査

### Phase 2: baseline

- NeSymReS GPU baselineはColab
- PySR baselineはローカル
- 同じproblem、seed、operator set、候補budgetを使用
- 成功式だけでなく全problem recordを保存

### Phase 3: probing / layer scan

- validationだけで軽量probing
- 高価なPhase 4へ渡す候補層を削減
- layer候補と選択規則を凍結
- 各層のlinear probe、CKAまたは同等の表現類似度、勾配・更新感度を保存
- 入力表現、変数選択、token生成、式構造回復に対応するprobe targetを分ける
- validation上の層別skeleton recoveryを集計し、`val_ce`順位との一致度（Spearman）を保存する。
  GPU_RUN1ではseed間順位安定性が`val_ce` 0.991、`sym_rate` 0.881であり、
  recoveryは層解析に使える信号を既に持っている

### Phase 4: contribution

- probeで残った候補をpaired seedで比較
- 単一層fine-tuningだけでなく、層ablationと固定したactivation介入を比較
- probe順位、fine-tuning順位、ablation効果、介入効果の一致度をseed別に報告
- full FTがbaseを改善しない指標は正規化rankingへ混ぜない
- raw base/full/layer scoreを保存
- beamとdecode timeoutを統一

### Phase 5: selective fine-tuning

- top/random/middle/bottom/fullの公平な比較
- random層集合は10本以上をdrawし、全層random・encoder限定random・寄与下位randomの3母集団を分ける
- 同じ初期checkpoint、データ順、候補数
- early stoppingと選択はvalidationのみ
- testは条件固定後に1回。`test_in_skeleton`と`test_novel_skeleton`を分けて集計する
- 全層同等性（margin `0.02`）とtop対random優越性を別の仮説として判定する
- NMSEが同等でも`test_in_skeleton`のskeleton recoveryが0なら、数式回復成功とは判定しない
- `test_novel_skeleton`の0は外挿限界として報告し、fine-tuningの失敗と読み替えない

### Phase 6: TPSR

- MCTS、BFGS、Transformer推論を個別profile
- GPU利用率が低ければlocal/Colab分離
- rollout、width、horizon、timeoutを事前固定
- NeSymReS beamとの候補評価回数またはwall timeを併記
- validation subsetで追加NMSE、valid rate、complexity、elapsedのGo/No-Go判定を行う
- 2×2（beam/TPSR × FTなし/selective FT）のpaired設計を維持し、
  「selective FT後にTPSR利得が縮小する」交互作用を事前登録した再現対象として判定する
- valid rateはTPSRで低下する（GPU_RUN1: selective FT下で`0.921`）ため、
  成功例のみの指標を使わずpenalized指標で比較する
- GPU_RUN1と同程度の費用対効果なら、全規模TPSRは行わず副次的な負の結果として確定する。
  ただし交互作用の判定に必要な最小規模は確保する

### Phase 7a: 微分推定sanity check（DREAM4本実行の前提）

- 真のODEが既知のDREAM4-like合成系を使用する
- 微分ターゲットを4条件（真の解析微分／有限差分／スプライン平滑化／積分形式）で比較する
- decodeパイプライン、operator set、timeout、seedは全条件で同一にする
- penalized NMSE、valid rate、variable F1を条件別に保存する
- 判定：真の微分でNMSEが十分下がるなら原因は微分推定側、下がらないならモデル・分布側とする
- この結果をPhase 7の解釈とselector改良への資源配分の根拠として記録する
- Phase 7a の結果に応じてPhase 7の微分推定法を選ぶ場合は、選択規則を実行前に固定する

### Phase 7: DREAM4

- 3 seeds × Size10/100 × network 1–5を維持する
- noiseは独立設定として記録
- target checkpointを最初から使用
- timeoutは全target一律15秒
- operator setを制限
- targetごとのelapsed distributionを保存
- network単位の完了を待たずDriveへ同期
- 主集計は全seed・全network完了後だけ作る
- oracle selectorと経験的selectorを分け、SR性能とregulator selection誤差を分解する
- 平均予測器（NMSE = 1）を基準線として全図表へ明示し、oracle条件との差を必ず併記する
- oracle条件でもNMSEが1近傍にとどまる場合は、selector改良ではなくPhase 7aの判定へ帰着させる
- network・targetごとに生の式、簡約式、実遺伝子名対応、holdout指標、安全性検査を保存する
- 新規性を主張する候補は既知の正解・既存辺との一致と不一致を分け、未検証候補として一覧化する
- 一部networkだけが完了した場合は主結果を作らず、未完了runとして保存する

Size100の約2,820 evaluationsがすべて15秒へ到達する場合:

```text
2820 × 15 / 3600 = 11.75時間
```

最大2 seed並列で3 seedを2組に分けて進める場合、各seedの負荷が同程度ならdecode上限は約7.8時間である。model load、fine-tuning、I/O、集計を含むため、Phase 7の安全な計画枠は8–14時間とする。
これは保証値ではなく、15秒hard timeoutから得られるbudget上限の目安である。

### Phase 8: human LODO

- NeSymReSはColab GPU
- PySRはローカルCPU
- 1式をin-donor/holdoutで再利用
- in-donor内にさらに式選択用の内部holdoutを設け、in-donor値が選択で楽観的にならないようにする
- 4 donor foldをcheckpoint
- timeoutは全target15秒
- PySRの全foldへ同じ15秒search timeoutと親process hard timeoutを適用する
- PySRはdeterministic serial、または事前規定した複数のmultithread反復のどちらかへ統一する
- NeSymReS、PySRのoperator差をなくし、候補評価数とwall timeを併記する（3.12節）
- fine-tuningに要したGPU時間をdecode budgetと別に記録し、合算も併記する
- donor別のholdout値を必ず個別に報告する。GPU_RUN1ではdonor 11でPySRのholdout NMSEが
  `0.729`へ跳ね、方法の順序が逆転した。`n=4` donorでは方法の順位づけを主張しない
- in-donorとholdoutの比（GPU_RUN1のPySRは約22倍）を過剰適合指標として保存する
- donor holdoutで安定した候補式について、実遺伝子名、式複雑度、特異点、外挿安定性、非負性を保存する
- human application demoとして限定解釈し、候補式を真の制御ODEまたは因果機構と呼ばない

### Phase 9: validate / archive

- Colabとローカル成果物を統合
- 必須ファイル、equation schema、failure reasonを検査
- config、commit、data checksumを照合
- archiveとSHA256作成
- graphs/tables生成
