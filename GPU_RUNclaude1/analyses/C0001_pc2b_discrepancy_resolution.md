# C0001 — PC2b の不一致（110/170 対 0/28）の解決

**日付**: 2026-09-09。**解決者**: supervisor、直接測定による。
**状態**: クローズ。凍結された v2.1 の期待値が正しく、実装側の測定が誤っていた。

## 何が食い違ったか

アフィン分解のコントロールである PC2b について、二つのエージェントが両立しない値を報告した。

- `lansr-reproducibility-auditor`（v2 監査、V2-CRIT-1）: M3 のスコアは **0**。測定値は 0/28 成分、
  0/80 システム。これを根拠に v2.1 は PC2b の期待値を **適格な全インスタンスで一致 0 件** に凍結し、
  非ゲート化して記述的扱いとし、E0 のアフィン分解機構（M-ii）は **C0001 では計測されない** と宣言して
  C0002 へ回した。
- `lansr-implementation-engineer`（Stage 4）: **110/170** を測定し、自分で手計算検証した代数を黙って
  上書きするのではなく、未解決としてフラグを立てた。これは正しい対応であり、このフラグがあったから
  解決できた。

これは見かけの問題ではない。もし M3 がアフィン分解を *証明できる* なら、M-ii には計測手段があることに
なり、v2.1 §1.3 のスコープ制限は誤りとなる。

## 決定的な測定

まず、素の代数。真の Hill 恒等式 `a*A/(K+A) = a - a*K/(K+A)` について:

```
mult : 2.05*x_0/(1.676 + x_0)              skeleton -> c*x_0/(c + x_0)
aff  : 2.05 - 2.05*1.676/(1.676 + x_0)     skeleton -> c*(c + x_0 + 1)/(c + x_0)
numerically identical : True
M3 skeleton match     : 0.0
```

関数としては完全に同一であるにもかかわらず、M3 は一致と判定しない。定数の潰し込み（constant collapse）は
`a` と `a*K` の両方を同一の記号 `c` へ写し、さらに式変形が `+ 1` の項を導入するため、二つの骨格は
構造的に異なる木になる。

次に、同じ問いを実データのコーパス上で、実装自身の書き換え
（`src/gpu_runclaude1/partb.py:349 rewrite_b_r1_affine_infix`）を検証用の真値成分 170 個すべてに適用し、
**成分単位** で採点した結果:

| 量 | 値 |
|---|---|
| 成分の総数 | 170 |
| 書き換えが発火した数 | **60** |
| そのうち **真の代数的恒等式** と検証された数 | **55** ← この値は撤回済み。正しくは **60**（下記「第二の所見 — 撤回」を参照） |
| そのうち **M3 が一致と判定した数** | **0** |

## 結論

**監査者が正しく、v2.1 の凍結期待値 0 が正しい。** M3 はアフィン分解を証明できない。同一性が検証済みの
60 件の書き換えに対してもできない。E0 の M-ii 機構には C0001 において実際に計測手段がなく、
C0002 へ回すのが正しい判断である。

**実装側が 110/170 を得た理由。** `src/gpu_runclaude1/controls.py:191 pc2b_affine_decomposition` は
システムの全成分を書き換えた後、`result.m3_system` を用いて **システム全体** を採点している:

```python
for c in components:
    new_c, did = rewrite_b_r1_affine_infix(c)
    rewritten.append(new_c)
    any_rewrite = any_rewrite or did
n_eligible += int(any_rewrite)
result = score_pair(_join(components), _join(rewritten))
passed = result.m3_system == 1.0
n_pass += int(passed and any_rewrite)
```

書き換えが no-op（何もしない）だった成分はそのまま追加されるため、自分自身と比較されて自明に一致する。
`any_rewrite` はシステム全体の OR なので、*いずれか* の成分が書き換えられればそのシステムは適格と
みなされる一方、システムのスコアは手を触れられていない成分に支配される。結果として得られるのは、
システムレベルの自明な一致件数を、成分レベルの分母に対して報告した数値である。これは監査側の量でも
事前登録された量でもない。

## 第二の所見 — 撤回: 書き換えは健全であり、誤っていたのは私の恒等式チェックだった

**私は当初、発火した 60 件の書き換えのうち 5 件は真の代数的恒等式ではないと本文書で報告し、Part B の
B-R1 を保留するよう指示した。その主張は撤回する。** 実装エンジニアはこの主張の受け入れを拒否し、
再測定によって実装側が正しいことが証明された。

発火した 60 件の書き換えは、**すべて** 真の代数的恒等式である:

| 検証方法 | 結果 |
|---|---|
| 厳密な有理数演算（`nsimplify(..., rational=True)`） | **60 / 60** |
| 正の 5 点での数値プローブ | **60 / 60** |
| 私が当初用いた素朴な Float の `simplify(a - b) == 0` | 55 / 60 |

私の方法が棄却した 5 件についての絶対差の最大値:

```
3.331e-16   0.1954 + 0.8878 * x_0 * 1/(0.8392 + x_0) + -1 * 0.3968 * x_0
4.441e-16   0.1085 + 1.912 * ((x_1)**2)**2 * 1/(0.4429 + ((x_1)**2)**2) + ...
2.220e-16   1.203 * ((x_0)**2)**2 * 1/(0.7487 + ((x_0)**2)**2) * 1 * ((x_1)**2)**2 ...
2.220e-16   2.119 * x_0 * 1/(1.388 + x_0) * 1 * x_1 * 1/(0.4059 + x_1) + ...
0.000e+00   1.146 * (x_0)**2 * 1/(1.013 + (x_0)**2) * 1 * (x_1)**2 * 1/(2.082 + ...
```

いずれも機械精度の範囲であり、最後の一件は差が **正確にゼロ** であるのに、私のチェックはそれでも
棄却していた。原因は、`sympy.simplify` が `Float` 係数を確実に打ち消せないことである。
**これはまさに v2.1 の監査が V21-MAJ-1 としてすでに文書化していた機構** — sympy の `Float`
非打ち消し — であり、私はその指摘を読んだ後で同じ誤りを犯した。

**撤回に伴う帰結:**
- `src/gpu_runclaude1/partb.py:349 rewrite_b_r1_affine_infix` は **健全** である。修正は不要。
- **B-R1 は保留しない。** 保留するという私の指示を撤回する。
- F2 は無意味（moot）だった。Part B 自身の `affine_rewrite_component` は独立に検査されており、
  未検証の書き換えを適用したことは一度もない。
- 本文書の **第一の** 所見（F1、還元レベル不一致の採点バグが 0/60 を見かけ上 110/170 に膨らませていた件）は
  **影響を受けず、有効なまま** である。実装者がこれを再現して修正し、PC2b は現在
  60 適格 / 0 一致、すなわち凍結された v2.1 の期待値そのものを測定している。
- 常設規則 **R4** は影響を受けず、F1 の証拠のみで成立する。

## 必要な対応

1. PC2b の測定を **成分レベル** に再規定し、書き換えが実際に発火した成分のみを比較して、実現した
   適格集合として `0/60` を報告する。これは v2.1 の凍結期待値 0 と整合する。凍結期待値は変わらず、
   変わるのは実装側の測定だけである。
2. ~~`rewrite_b_r1_affine_infix` を修正し、発火する書き換えのすべてが検証済みの代数的恒等式となるように
   して、その検証を B-R1 のゲート条件とする。~~ **この対応要求は撤回した。** 下記「第二の所見 — 撤回」の
   とおり、60 件の書き換えはすべて真の恒等式であり、`rewrite_b_r1_affine_infix` に修正は不要で、
   B-R1 を保留する理由もない。非恒等式が 5 件あるとした私の判定自体が、素朴な Float 比較による
   偽陰性だった。
3. v2.1 §14 項目 11 の読み方を保持する。すなわち、PC2b が非ゼロであればそれはハーネスの差異を示すもので
   あって科学的発見ではない。今回の一件はまさにその事例であり、実際にハーネスの差異だった。

## プロセスについての注記

どちらのエージェントも不注意ではなかった。監査者は、より小さな構成（28 成分）上で正しい量を測定した。
実装者は、より大きな構成上で別の量を測定し、**自分の代数と矛盾する結果を上書きすることを拒んで**
対立を表面化させた。凍結されたコントロールに対する二つの独立した測定が食い違うことは、まさに
コントロール群（control battery）が生み出すべきシグナルであり、それが本番実行の後ではなく前に発火した。
常設規則 R2 の「母集団が仮定した性質を持つことを検証する」ではこの事例は捕まえられない。
ここでの教訓はより狭く、R4 として追加する。
